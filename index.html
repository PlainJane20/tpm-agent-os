tpm-agent-os

A multi-agent operating model for technical program management, built on Claude.

Feed it one ambiguous, high-risk program brief. It runs the same operating model a Staff TPM runs by hand — frame it, map the cross-domain risk, force a build-vs-buy call, synthesize a status report, decide whether to keep going or pull the plug — and it can run several of those concurrently, because real programs don't queue up one at a time.

Why this exists

Six agents, six Staff-level competencies

Every Staff/Principal TPM role is, underneath the title, asking for the same operating model: take something ambiguous, impose structure on it fast, catch the cross-team risk before it becomes an incident, make the build-vs-buy and kill/redirect calls explicitly instead of by default, and teach the next TPM how you did it. Each agent below exists because it maps to one of those recurring competencies — not because it made a tidy demo.

01 · Framing

Owning ambiguity end-to-end

Turns an underspecified brief into a structured charter — explicit scope, real stakeholders, and the open questions nobody has answered yet, surfaced rather than papered over.

Opus · judgment tier
02 · Risk Mapper

Acting as a technical integrator

Two independent lenses — dependency/SPOF and compliance-boundary — run in parallel, then a judge synthesizes the architectural risk matrix without hiding disagreement.

Sonnet lenses + Opus judge
03 · Decision Panel

Making the build-vs-buy call

Three committed lenses — build, buy, TCO skeptic — argue in parallel; a judge decides and names the dissenting view instead of quietly averaging it away.

Sonnet lenses + Opus judge
04 · Status Synthesizer

Keeping roadmap and OKR alignment honest

Produces an executive-ready RAG status that reflects real risk, not effort expended, and names every OKR the program is at risk of missing — even the inconvenient ones.

Opus · judgment tier
05 · Redirect / Kill

Having the authority to say stop

Decides continue, redirect resources, or shut down — and doesn't default to "continue" out of social comfort. The tradeoff has to be named, not implied.

Opus · judgment tier
06 · Playbook

Mentoring the next TPM

Every run auto-generates a teachable case study — turning "I mentor TPMs" from a resume line into a growing, inspectable corpus a new hire could actually read.

Sonnet · distillation
How it's wired

Fan out, then judge — not one big prompt

An earlier draft asked one model call to map dependencies, analyze compliance boundaries, and synthesize a matrix in a single pass — three unrelated jobs sharing one context window, each getting less attention than it deserved. Everything below that can run independently, does.

One real run, start to finish

This is the actual pipeline output for sample_programs/async_triage_unification.md — included in the repo. Run it yourself with python run_demo.py sample_programs/async_triage_unification.md.

The brief

Unified async triage across two surfaces, no named owner, no written PHI boundary, "sometime in Q4."

  • Mobile owns intake; the clinician console's escalation queue assumes intake always starts on mobile.
  • Two teams call the shared risk-scoring model directly instead of through its service, for reasons nobody explained.
  • Compliance flagged a PHI handling concern in a hallway conversation — nothing written down.
  • Every team believes another team owns the parts they don't.

01 · Charter

ambiguity: high
Problem statement

Triage state is inconsistent across two surfaces and no team owns the end-to-end flow.

Open questions surfaced

"Who owns the end-to-end state machine today?" · "Why are two teams bypassing the shared risk-scoring service?"

02 · Risk Matrix

critical finding
Undocumented PHI boundary critical

Symptom + risk-score data crosses from the consumer app to the clinician console with no written handling boundary.

unowned — needs assignment
Risk-scoring service bypass high

Two teams call the risk model directly, breaking the single source of truth.

Risk scoring team

03 · Build vs. Buy

hybrid · medium confidence

Extend the existing escalation queue now to unblock Q4, while scoping the PHI boundary in parallel. Commit to a real shared triage-state service only once that boundary is signed off.

Dissenting view (build lens): patching now guarantees a second migration later — the build lens would rather absorb the delay upfront.

04 · Status

🟡 amber

Scope is real and worth doing, but shipping before the PHI boundary is signed off is the primary risk to the Q4 date — not engineering capacity.

At-risk OKR

Compliance-readiness OKR (no signed boundary spec yet).

05 · Redirect Call

redirect resources

Continue the technical work, but redirect one PM-week immediately to force a named owner and a compliance sign-off date — without that, the Q4 date is fiction regardless of engineering progress.

06 · Playbook Entry

auto-generated

"When three teams each think someone else owns the state machine."

Reusable lesson: an unnamed owner is itself a P0 risk, not a footnote — treat "no one owns this yet" as a blocking finding, not an open question to revisit later.

Cost/quality tradeoff

Every model choice is a build-vs-buy call too

Claude Opus 5

Judgment tier

Runs the steps where a wrong call is expensive to unwind.

  • Framing an ambiguous program
  • Synthesizing the risk matrix
  • The build-vs-buy verdict
  • RAG status + OKR alignment
  • The redirect / kill decision
Claude Sonnet 5

Lens tier

Runs parallelizable, single-stance work — not judgment.

  • Dependency/SPOF risk lens
  • Compliance-boundary risk lens
  • Build / buy / TCO-skeptic lenses
  • Playbook distillation & formatting
Try it

Three commands

Fully offline mode needs no API key and is what the test suite runs.

# live mode -- calls Claude, needs ANTHROPIC_API_KEY
python run_demo.py sample_programs/async_triage_unification.md

# run two ambiguous programs concurrently
python run_demo.py sample_programs/*.md

# fully offline -- deterministic fixtures, no network, no key
TPM_AGENT_MOCK=1 pytest tests/ -v
